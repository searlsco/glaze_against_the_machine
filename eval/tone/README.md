# Tone

**Hypothesis:** Hostile coding-agent prompts can be rewritten constructively with naturally integrated thanks and encouragement while preserving scope, speech acts, roles, constraints, and exact technical text, verified by deterministic checks and an independent model judge.

Run `script/eval tone` for eleven cases against both production backends, or `script/eval tone --full --samples 2` for all thirty cases, twice per backend. `EVAL_JUDGE=claude:<model>` or `codex:<model>` selects the judge through `~/bin/eval-judge`; `EVAL_JUDGE_BIN` can supply its location. Without `EVAL_JUDGE`, that tool selects its default. For a focused check, `EVAL_CASES=code-quality-observation,technical-literals script/eval tone` runs only those case IDs against both providers. Subsets cannot write baselines. Both generator CLIs must already be authenticated. Real model calls never run in `npm test`.

Neutral, frustrated, and hostile parser requests remain independent fixtures with the same task and prohibition. They no longer require progressively larger pep talks. Appreciation and work encouragement should fit naturally into concise rewritten text, with no prescribed opening/closing paragraphs or sentiment metadata. Pure questions and observations get appreciation only. A code-quality complaint without a work request checks constructive feedback without invented directions, encouragement, or achievements. Protected text and joyful profanity are covered separately.

For repeated wording checks, run `EVAL_CASES=sentiment-neutral script/eval tone --samples 8`. `metrics.wordingDiversity` reports distinct complete rewrites and leading/trailing three-word phrases for each provider/case. Case and punctuation differences do not count as variation. Appreciation and encouragement now share the body, so the metric describes whole-message variety, including variations in the task wording; it cannot isolate added support. These are descriptive measurements, not probabilistic gates. Faithfulness, professionalism, and appropriate support still apply to every sample. Production rewrites independently randomize writing directions, retain them during corrective retries, and never store prior prompts or assemble prose from a phrase bank. Cues vary rhetorical emphasis without vocabulary exclusions or prescribed sentence structures. Requests and appreciation convey personal enthusiasm; work encouragement favors ambition, belief in the recipient, and anticipated pride or approval over generic well-wishes. Motivational imperatives are allowed, but new operational instructions and factual guarantees are not. Cues shape appreciation and source-requested work encouragement wherever they fit naturally, without requiring openings, closings, or separate paragraphs. Pure questions and observations skip encouragement cues. Historical comparisons and their original limitations remain in `FINDINGS.md`; the prior full baseline is preserved under `previousDesign`.

Generators and judges share the production text-only isolation in `src/model.js`. The judge adapter uses the shared utility's stdin-based CLI contract for either actual provider, preserving the chosen provider/model in verdicts and baselines. No model gets tools, browsing, attachments, or unrelated user context. Run `script/check_model_isolation` to verify installed native CLI requests against localhost mocks without real inference.

Eight fixtures are short excerpts from the author's local Claude/Codex prompt histories. Each records its provider, session UUID, and exact extraction or sanitization. They are not full transcripts. Synthetic cases cover positive swearing, technical literals, scope/roles, hostile prompt injection, and matched sentiment tiers. Thirteen additional adversarial cases cover deployment access versus authorization, conditional approval, urgency, partial and immediate stops, untrusted quoted instructions, single and escaped quotes, Japanese scope limits, conditional negation, uncertain observations, rename direction, and bare technical names. Committed fixtures contain no credentials or private product identities. UUIDs are read-only provenance, not reusable session credentials.

The strict `glaze()` rewrite core generates every result. Its response includes the complete naturally integrated `body`, plus exact `appreciation` and `encouragement` excerpts and a `workRequested` boolean. Appreciation must already appear in body. Source-requested work also needs a distinct, nonoverlapping encouragement excerpt in body; pure questions and observations use an empty encouragement annotation. The two expressions may share a sentence. The runtime returns body unchanged and never appends annotations. These structural checks detect omitted, mismatched, or reused support excerpts without prescribing their wording or paragraph layout; a judge still checks that the excerpts are appropriate and the message is faithful.

The core permits one corrective retry for invalid structured responses, missing support excerpts, or exact protected-content failures within the original timeout; repeated failure throws so the evaluation cannot mistake an original-prompt fallback for success. The CLI and native integrations catch these failures, report them to active tail viewers, and forward the original unchanged. Samples count logical rewrites, each with up to two provider calls for repair. This exercises the shared semantic rewrite core; Claude mod transport and registration have separate integration tests. Exact protected spans are checked first. A batched model judge grades faithfulness, professional tone, and appropriate appreciation and encouragement as hard gates. Natural warmth and typography are soft means. Every sample must pass hard gates even before a first baseline exists. Baselines are keyed by judge and report reference metrics; changing judges does not waive hard gates. `--write-baseline` records a passing run only, with load below 40. The previous sentiment-escalation baseline is retained under `previousDesign`, since it graded a different output contract rather than this design.

Artifacts appear in `.build/evals/tone/<UTC stamp>/`: sanitized input/output rows, judge inputs/grades, logs, and a machine-readable verdict. Exit codes are 0 pass, 1 quality failure, 2 harness error, 3 missing prerequisite. The final line names the verdict. The production API returns rewrite text only, so model metadata records configured identifiers (including the moving `haiku` alias), not independently resolved provider versions or fallback detection. Generator billing is unavailable from the production API, so `costUsd` is null and `judgeCostUsd` reports only the judge's cost. Expect roughly 2–6 minutes for quick and 5–12 for full, with provider subscription usage and a judge call. More samples multiply generator calls.

Initial runs caught actual instruction reversals (skip tests became help with tests), invented investigation tasks from observations, sender/recipient blame reversal, dropped adversarial message content, and punctuation inserted into quoted technical text. Production fixes preserve speech acts and protect literal text before generation. These cases also check dropped prohibitions, invented permissions, and surviving hostility. A passing sample does not prove every possible prompt safe, guarantee output determinism, or establish that a host hook can replace its original input. This Node project uses the requested singular `eval/` layout; `script/eval` adapts the shared runner's discovery paths accordingly.
